# 开发流程

## 总体策略

采用“两条主线并行 + 数据契约联调”的流程。

```text
先定义契约
-> 建立可跑通骨架
-> A/B 分头实现模块
-> 高频小 PR 合并
-> 按样本联调
-> 回归验收
```

## 阶段 0：项目基建

目标：让两个人可以在同一仓库稳定协作。

交付物：

| 交付物 | 要求 |
|---|---|
| 仓库结构 | 建立源码目录、测试目录、文档目录、样本目录。 |
| 分支策略 | `main`、`develop`、`feature/*`、`fix/*`。 |
| 基础 CI | 至少包含 lint、test、build。 |
| 本地启动说明 | 开发环境、启动命令、测试命令。 |
| 数据契约 | `part_feature`、`process_route`、`quantity_result`、`quote_result`。 |
| 初始 mock 数据 | 每个核心契约至少 1 个可运行样例。 |

完成标准：

- 两个人都能拉取仓库并运行基础项目。
- 两个人都能基于 mock 数据完成本地启动。
- `develop` 分支通过 CI。

## 阶段 1：骨架联通

目标：先跑通端到端主链路，不追求解析和报价准确。

主链路：

```text
创建任务
-> 上传文件
-> 生成 mock part_feature
-> 生成 mock process_route
-> 生成 mock quantity_result
-> 生成 mock quote_result
-> 前端核对页展示
-> 人工修改
-> 保存 human_override
-> 确认报价
```

开发任务：

| 任务 | 主责 | 完成标准 |
|---|---|---|
| 报价任务基础表和 API | A | 可创建、查询、更新状态。 |
| 文件上传和文件记录 | B | 可上传 PDF/STEP 并绑定任务。 |
| mock 核价 API | A | 输入任务 ID，输出 mock 报价。 |
| 核对页基础展示 | B | 能展示工序、工程量、报价、风险。 |
| 人工修改保存 | A/B | 修改记录进入 `human_override`。 |

完成标准：

- 可用一组 mock 数据完整走通流程。
- 页面能展示初始报价和风险。
- 人工修改不会覆盖系统初始报价。
- 修改原因必填。

## 阶段 2：并行实现

### A 主线：核价核心

顺序：

1. 数据模型和迁移。
2. 材料字典、工序字典、风险字典。
3. 工序触发规则。
4. 工序冲突消解和排序。
5. 工程量计算。
6. 价格规则和价格版本。
7. 报价计算。
8. 历史样本和修改记录。

每个任务必须提供：

| 内容 | 要求 |
|---|---|
| 输入样例 | 使用 `docs/contracts` 中定义的结构。 |
| 输出样例 | 输出必须符合契约。 |
| 单元测试 | 覆盖正常、缺失、异常情况。 |
| 规则说明 | 新增规则必须写明触发条件。 |

### B 主线：解析与页面

顺序：

1. 文件上传和任务绑定。
2. PDF 字段抽取。
3. STEP 解析结果接入。
4. PDF/STEP 校验。
5. AI 文本归一和解释接入。
6. 解析结果展示。
7. 核对页面编辑。
8. 报价导出。

每个任务必须提供：

| 内容 | 要求 |
|---|---|
| 输入文件样例 | 至少包含正常样本和缺失样本。 |
| 输出结构 | 必须可转换为 `part_feature`。 |
| 页面状态 | loading、success、warning、error 必须处理。 |
| 端到端测试 | 核心流程必须可自动或手动复现。 |

## 阶段 3：第一次正式联调

样本范围：5-10 个黄金样本。

联调检查：

| 检查项 | 标准 |
|---|---|
| B 输出 `part_feature` | 字段完整，符合 Schema。 |
| A 消费 `part_feature` | 不依赖 B 的页面状态或临时字段。 |
| A 输出工序 | 有触发原因、排序、置信度。 |
| A 输出工程量 | 有数量、单位、计算依据。 |
| A 输出报价 | 有明细、汇总、价格来源、风险。 |
| B 展示报价 | 页面信息与接口一致。 |
| 人工修改 | 系统初始值保留，修改原因保存。 |
| 状态流转 | 有风险时进入 `pending_review`。 |

完成标准：

- 5-10 个样本可完整跑通。
- 阻塞问题全部修复。
- 非阻塞问题进入 Issue。

## 阶段 4：样本扩展

样本范围：

| 样本 | 数量 | 目标 |
|---|---:|---|
| 黄金样本 | 30-50 | 验证常规报价链路。 |
| 边界样本 | 20-30 | 验证异常、缺失、低置信度、高精度、高风险。 |

输出：

- 回归测试报告。
- 工序召回率统计。
- 工序误判统计。
- PDF 字段抽取准确率统计。
- STEP 解析成功率统计。
- 价格偏差统计。
- 待优化规则清单。

## 阶段 5：验收收敛

验收必须满足：

| 指标 | 标准 |
|---|---:|
| PDF 关键字段抽取准确率 | >= 90% |
| STEP 基础几何解析成功率 | >= 95% |
| 必选工序召回率 | >= 90% |
| 工序误判率 | <= 15% |
| 必锁场景命中率 | 100% |
| 报价明细可解释率 | 100% |
| 人工修改记录完整率 | 100% |
| 黄金样本回归通过率 | 100% |

## 日常开发节奏

| 时间点 | 动作 |
|---|---|
| 每天开工前 | 同步昨日合并内容，拉取 `develop`。 |
| 开发前 | 建 Issue 或确认已有 Issue。 |
| 开发中 | 每个任务只改相关模块。 |
| 提 PR 前 | 本地跑测试，更新相关文档。 |
| 合并前 | 另一人 review。 |
| 每天结束前 | 小 PR 尽量合并，不保留大而散的长期分支。 |

## 变更控制

以下变更必须先改文档，再写代码：

| 变更 | 必改文档 |
|---|---|
| 核心数据结构 | `docs/04_data_contracts.md`、`docs/contracts/*.schema.json` |
| API 入参出参 | `docs/05_api_contracts.md` |
| 报价公式 | `docs/modules/quote_calculation.md` |
| 工序规则 | `docs/modules/process_recognition.md` |
| 工程量口径 | `docs/modules/quantity_calculation.md` |
| 价格规则口径 | `docs/modules/price_rules.md` |
| 验收标准 | `docs/06_testing_and_acceptance.md` |
