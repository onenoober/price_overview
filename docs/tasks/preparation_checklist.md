# 开发准备清单

## 目标

两个人用简单方式协作，不引入复杂流程。准备工作只需要保证：能拉代码、能分开开发、能合并、能联调。

## 1. GitHub 权限

需要确认：

| 项 | 要求 |
|---|---|
| 仓库 | `https://github.com/onenoober/price_overview` |
| A 权限 | 至少有 push 权限。 |
| B 权限 | 至少有 push 权限。 |
| 本地 Git | 两个人都能 `git clone`。 |
| 身份配置 | 两个人本地 Git 有自己的 user.name 和 user.email。 |

检查命令：

```bash
git config user.name
git config user.email
```

## 2. 简单分支方式

推荐只用三个长期分支：

| 分支 | 谁用 | 用途 |
|---|---|---|
| `main` | 两人共同 | 可运行、可演示版本。 |
| `dev-a` | A | A 的核价核心开发。 |
| `dev-b` | B | B 的解析和页面开发。 |

使用规则：

- A 平时在 `dev-a` 开发。
- B 平时在 `dev-b` 开发。
- 功能能跑通后合并回 `main`。
- 合并前先和对方说一声，避免覆盖。

不强制 PR，但建议重要改动用 PR。

## 3. 初始仓库准备

需要放入仓库：

| 内容 | 状态 |
|---|---|
| `docs/` 文档 | 已加入。 |
| `docs/contracts/*.schema.json` | 已加入。 |
| `README.md` 文档入口 | 已加入。 |
| 项目源码目录 | 待确定技术栈后建立。 |
| 样本目录 | 待补充。 |
| 启动说明 | 待技术栈确定后补充。 |

建议后续建立：

```text
src/
tests/
fixtures/
fixtures/golden_samples/
fixtures/boundary_samples/
```

## 4. 第一次开发前必须确定

| 问题 | 建议 |
|---|---|
| 技术栈 | 先确定后端、前端、数据库。 |
| 本地启动方式 | 写入 README。 |
| 数据库存储 | 先选一种，不要 A/B 各自选。 |
| 文件存储 | 先本地存储即可。 |
| AI 接入方式 | 先封装接口，主流程可 mock。 |
| STEP 解析方案 | 先确定库或外部工具。 |
| PDF 解析方案 | 先确定 text layer + 多模态图像解析方案。 |

## 5. 第一周建议任务

A：

1. 建立基础数据模型。
2. 建立材料、工序、风险、单位字典。
3. 建立 mock `part_feature` 到 mock `quote_result` 的后端链路。

B：

1. 建立文件上传页面或接口。
2. 建立 mock `part_feature` 输出。
3. 建立核对页面，先展示 mock `quote_result`。

共同：

1. 确认 `part_feature` 契约是否够用。
2. 用一个样本跑通 mock 主链路。
3. 记录第一批联调问题。

## 6. 简单合并规则

每次合并前确认：

| 检查 | 要求 |
|---|---|
| 能启动 | 至少本地不报错。 |
| 不乱改 | 不修改对方负责模块的核心逻辑。 |
| 文档同步 | 改契约或接口时同步改文档。 |
| 有说明 | 合并时说明改了什么、怎么验证。 |

## 7. 最小联调目标

第一次联调只追求跑通：

```text
创建任务
-> 上传文件
-> 生成 mock part_feature
-> A 生成 mock quote_result
-> B 页面展示
-> 人工修改
-> 保存修改原因
-> 确认报价
```

这条链路跑通后，再逐步替换真实 PDF 解析、STEP 解析、真实规则和真实价格。
